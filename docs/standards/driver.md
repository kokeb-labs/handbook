# Driver contract

What every `driver-<chip>` repository provides. A driver is an MCU-agnostic C++20 template on a CRTP port: the
user writes the port for their MCU, and the driver works the same on ESP32, STM32, any other MCU or a host. ESP32
is the first example platform, not a dependency.

A driver carries no brand ([ADR-0012](../adr/0012-unbranded-drivers.md)): it is usable, and forkable, without
anything else from Kokeb Labs. Examples below use a fictional ZP100 pressure sensor on I2C; replace `zp100` /
`ZP100` with the chip.

## Repository layout

```text
driver-<chip>/
├── inc/
│   ├── <chip>.hpp                 umbrella header: the only one users include
│   ├── <chip>_<bus>_interface.hpp the CRTP port base and its pin enums
│   ├── <chip>_types.hpp           Error, Result<T>, Config, enums
│   ├── <chip>_registers.hpp       register map (optional)
│   ├── <chip>_kconfig.hpp         optional: maps CONFIG_<CHIP>_* onto Config defaults
│   └── <chip>_version.h.in        version template, generated by CMake
├── src/<chip>.ipp                 template implementation, included at the end of <chip>.hpp
├── cmake/<chip>_build_settings.cmake   version, target name, sources: the single source of truth
├── cmake/<chip>Config.cmake.in
├── examples/
│   ├── host/                      runs on any PC: host port over the register model, built and run in CI
│   └── <platform>/                one self-contained folder per platform with its own port (esp32/: ESP-IDF)
├── tests/                         host tests, doc snippets, install consumer
├── docs/                          the driver page set (see docs.md)
├── _config/                       all tool configuration: org .clang-format and .clang-tidy, Doxyfile,
│                                  mkdocs.yml (docs_dir: ../docs), Kconfig, markdownlint, yamllint, lychee
├── .github/                       workflows, CONTRIBUTING.md, SECURITY.md, CODEOWNERS, templates
├── .claude/                       agent skills
├── CMakeLists.txt                 the CMake library, and under ESP_PLATFORM the ESP-IDF component
├── driver.yml                     driver metadata: bus, supported MCUs, minimum kb-core
└── README.md, LICENSE (MIT), CHANGELOG.md, AGENTS.md, CLAUDE.md, .gitignore, .gitmodules
```

The root holds only these entries ([ADR-0011](../adr/0011-repository-root-layout.md)): what GitHub or a tool needs at
the root and what a reader looks for first. Tool configuration MUST live in `_config/`, and every command and
workflow names its path; the root MUST NOT hold copies of or symlinks to it.

## Names

([ADR-0012](../adr/0012-unbranded-drivers.md))

| Thing | Name | Example |
| --- | --- | --- |
| Repository | `driver-<chip>` | `driver-pcal95555` |
| Namespace | `<chip>` | `pcal95555` |
| Driver class | `<chip>::<CHIP>` | `pcal95555::PCAL95555` |
| Umbrella header | `inc/<chip>.hpp` | `inc/pcal95555.hpp` |
| CMake package and target | `find_package(<chip>)`, `<chip>::<chip>` | `find_package(pcal95555)`, `pcal95555::pcal95555` |
| Build settings | `cmake/<chip>_build_settings.cmake` | `cmake/pcal95555_build_settings.cmake` |
| Macros and CMake options | `<CHIP>_*` | `PCAL95555_VERSION_MAJOR`, `PCAL95555_BUILD_TESTS` |
| Kconfig | `CONFIG_<CHIP>_*` | `CONFIG_PCAL95555_I2C_ADDRESS` |

- A driver MUST NOT contain an org prefix: no `kb_`, `kb::`, `KB_` or any other brand in a name, namespace, macro,
  target, file or option. A fork MUST NOT inherit one.
- Everything MUST be inside `namespace <chip>` (lower case, the part number: `zp100`, `tmc9660`). Nothing is
  declared at global scope, including free `GetDriverVersion()` helpers and `using` declarations.
- The driver class MUST be `<chip>::<CHIP>` with the part number in upper case: `zp100::ZP100`. Not `Device`,
  `Driver` or a product name.
- A driver for a family names the class after the family member it was written for and lists the others in the
  README (`at25040::AT25040` also drives AT25010B and AT25020B).
- Naming inside the namespace follows [naming-and-style.md](naming-and-style.md).

## Platforms

- Driver code (`inc/`, `src/`) MUST NOT include an SDK, RTOS or vendor header. Platform code lives only in
  `examples/<platform>/`: each folder carries its own port, an example program and a README, and builds on its own.
- Every driver MUST ship `examples/host/`: a host port over the test register model and a program that initialises
  the driver and reads it, built with the test flags and run by the host tests. It is the quickstart's first step.
- A platform is added only with a CI job that builds its example. Plain CMake covers STM32, RP2040, nRF and the
  host; the root `CMakeLists.txt` covers ESP-IDF. Zephyr, Arduino or PlatformIO manifests are added only when a
  user needs them, never as a second copy of the sources.
- A driver that needs one MCU's peripheral is the documented case in [MCU-bound drivers](#mcu-bound-drivers).

## The port

The port is how the driver reaches the bus. The user derives a class from the driver's CRTP base and implements
its hooks; the driver is a template on that class.

```cpp
// inc/zp100_i2c_interface.hpp
namespace zp100 {

enum class CtrlPin : uint8_t { Int = 0 };                  // logical pins, not MCU pin numbers
enum class GpioSignal : uint8_t { INACTIVE = 0, ACTIVE = 1 };

template <typename Derived>
class I2cInterface {
public:
  I2cInterface(const I2cInterface&) = delete;
  I2cInterface& operator=(const I2cInterface&) = delete;

protected:
  I2cInterface() = default;
  ~I2cInterface() = default;
};

/// Satisfied by a class that derives from I2cInterface<P> and implements the required hooks.
template <typename P>
concept I2cPort = std::derived_from<P, I2cInterface<P>> &&
                  requires(P& p, uint8_t addr, const uint8_t* tx, uint8_t* rx, size_t n) {
                    { p.EnsureInitialized() } -> std::same_as<bool>;
                    { p.Write(addr, tx, n) } -> std::same_as<bool>;
                    { p.WriteRead(addr, tx, n, rx, n) } -> std::same_as<bool>;
                  };

} // namespace zp100
```

```cpp
// The user's port, for their MCU
class MyI2c : public zp100::I2cInterface<MyI2c> {
public:
  bool EnsureInitialized() noexcept;
  bool Write(uint8_t addr, const uint8_t* data, size_t len) noexcept;
  bool WriteRead(uint8_t addr, const uint8_t* tx, size_t tx_len, uint8_t* rx, size_t rx_len) noexcept;
  void DelayUs(uint32_t us) noexcept;  // optional hook
};
```

Rules:

- The base MUST be named `<chip>::{Spi,I2c,Uart,Adc}Interface<Derived>` and the concept `<chip>::{Spi,I2c,Uart,Adc}Port`.
  A chip with two buses has one base per bus. There are no virtual functions.
- The driver template MUST be constrained by the concept (`template <I2cPort Port> class ZP100`), so a missing or
  misspelt hook is a compile error at the point of use.
- The base MUST NOT declare the required hooks itself. A forwarding hook in the base turns a missing override into
  infinite recursion at run time. The base MAY provide helpers built on hooks (`GpioSetActive(pin)`).
- Hooks MUST be PascalCase, `noexcept`, and return `bool` (`true` = the transfer completed). A `void` hook hides
  bus errors and is not allowed.
- Hooks move raw bytes only. The driver MUST NOT configure the bus (speed, mode, pins); the port or the board does.
  Register addresses travel in the payload.
- `EnsureInitialized()` on the port brings the bus up on first use and is idempotent.
- Pins are logical: `CtrlPin` names the chip's function (`Reset`, `Int`, `Enable`) and `GpioSignal::ACTIVE` means
  "function asserted", whatever the electrical polarity. The port maps both to the board.

### Required hooks per bus

| Bus | Hooks |
| --- | --- |
| SPI | `bool Transfer(const uint8_t* tx, uint8_t* rx, size_t len)`: one full-duplex transaction with chip select asserted for its whole length; `tx` or `rx` may be `nullptr` |
| I2C | `bool Write(uint8_t addr, const uint8_t* data, size_t len)`, `bool WriteRead(uint8_t addr, const uint8_t* tx, size_t tx_len, uint8_t* rx, size_t rx_len)` (repeated start); `bool Read(uint8_t addr, uint8_t* data, size_t len)` when the chip needs it |
| UART | `bool Write(const uint8_t* data, size_t len)`, `bool Read(uint8_t* data, size_t len, uint32_t timeout_ms)` (all `len` bytes or `false`), `bool FlushInput()` |
| ADC | `bool ReadVoltageMv(uint8_t channel, uint32_t& voltage_mv)` |

All of them plus `bool EnsureInitialized()`. A chip with a protocol that does not fit (a multi-phase frame, a
DMA stream) MAY add hooks; they follow the same rules and are listed on the Porting page.

### Optional hooks

| Hook | When missing |
| --- | --- |
| `void DelayUs(uint32_t us)`, `void DelayMs(uint32_t ms)` | Compile error at the first call that needs the wait. A driver whose chip has a timing requirement MUST NOT skip the wait. |
| `bool GpioSet(CtrlPin pin, GpioSignal signal)` | The function that needs the pin returns `Error::Unsupported`, or the driver uses the documented software alternative (for example a soft reset instead of the reset pin). |
| `bool GpioRead(CtrlPin pin, GpioSignal& signal)` | Same as `GpioSet`; interrupt-driven reads fall back to polling a status register when the chip has one. |
| `void Log(LogLevel level, const char* fmt, ...)` | No output. The driver never formats text itself. |

Optional hooks MUST be detected with a C++20 `requires` expression in one place, never with `void_t` or by
calling through the base:

```cpp
namespace zp100::detail {

template <typename Port>
void DelayUs(Port& port, uint32_t us) noexcept {
  if constexpr (requires { port.DelayUs(us); }) {
    port.DelayUs(us);
  } else {
    static_assert(sizeof(Port) == 0, "zp100: the port must implement DelayUs(uint32_t)");
  }
}

} // namespace zp100::detail
```

A missing hook therefore either falls back in a documented, safe way or fails to compile. It never silently
skips a step.

## Errors and `Result<T>`

Each driver has its own error enum and result type, so it stays usable outside kb-core
([ADR-0001](../adr/0001-error-model.md)). Handlers map them to `kb::Status` ([errors.md](errors.md)).

```cpp
namespace zp100 {

enum class Error : uint8_t {
  // Base set: every driver declares these, with these values, in this order.
  Ok = 0,
  NotInitialized = 1,   // an I/O call before Initialize() succeeded
  InvalidArgument = 2,  // a parameter outside the documented range; nothing was sent
  Bus = 3,              // a port hook returned false
  Timeout = 4,          // the chip did not become ready in time
  DeviceIdMismatch = 5, // the ID register did not match the part
  Crc = 6,              // a frame failed its CRC or checksum
  Busy = 7,             // the chip refused the command because it is busy
  DeviceFault = 8,      // the chip reported a fault (status register, error frame)
  Unsupported = 9,      // the hook or feature this call needs is absent
  // Chip-specific values start at 16.
  FifoOverflow = 16,
};

[[nodiscard]] constexpr const char* ToString(Error error) noexcept;

template <typename T>
struct [[nodiscard]] Result {
  T value{};
  Error error{Error::Ok};
  [[nodiscard]] constexpr bool ok() const noexcept { return error == Error::Ok; }
  constexpr explicit operator bool() const noexcept { return ok(); }
};

template <>
struct [[nodiscard]] Result<void> {
  Error error{Error::Ok};
  [[nodiscard]] constexpr bool ok() const noexcept { return error == Error::Ok; }
  constexpr explicit operator bool() const noexcept { return ok(); }
};

} // namespace zp100
```

Rules:

- Every public call that can fail MUST return `Result<T>` (or `Result<void>`). No `bool` success flags, no
  out-parameter plus `bool`, no error code read back from a getter.
- The base set MUST be declared with the values above, so one mapping table serves every driver. A driver MAY
  never return some base values; its API guide says which.
- Each chip-specific value MUST be returned by at least one call. Unused values are deleted.
- Every port failure MUST propagate as `Error::Bus` (or `Crc`, `Timeout` when that is what happened). A getter that
  returns a stale or zero value after a failed read is a defect.
- `T` MUST be default-constructible and trivially copyable. A failed call leaves `value` default-initialised.
- Sticky chip status (fault latches, error counters) is extra: a getter MAY expose it, but it never replaces the
  `Result` of the call that hit the error.
- `ToString()` returns a static string for every value.

## Lifecycle

([ADR-0002](../adr/0002-lifecycle.md))

```cpp
template <I2cPort Port>
class ZP100 {
public:
  explicit ZP100(Port& port, uint8_t address = kDefaultAddress) noexcept;  // stores, no I/O

  Result<void> Initialize(const Config& config = {}) noexcept;  // reset, check chip ID, apply config
  Result<void> EnsureInitialized() noexcept;                     // Initialize(last config) once
  [[nodiscard]] bool IsInitialized() const noexcept;
  Result<void> Deinitialize() noexcept;                          // chip to its safe low-power state

  Result<float> ReadPressurePa() noexcept;
  Result<void> SetOversampling(Oversampling osr) noexcept;
};
```

- The constructor MUST be `noexcept`, MUST NOT perform I/O and MUST NOT fail. It stores references and defaults.
- `Initialize(config)` MUST, in order: call the port's `EnsureInitialized()` (`Bus` on failure), reset the chip
  (hardware reset if the pin hook exists, else software reset), read and check the chip ID (`DeviceIdMismatch`),
  apply `config`, and only then mark the driver initialised. On any failure the driver stays uninitialised.
- `EnsureInitialized()` returns `Ok` at once when initialised; otherwise it runs `Initialize()` with the last
  config passed (or the default). It is the call handlers use.
- `Deinitialize()` puts the chip in its documented safe state (outputs off, low-power mode) and clears the
  initialised flag. Calling it on an uninitialised driver returns `Ok`.
- Every call that touches the bus MUST return `NotInitialized` before `Initialize()` succeeded. No call resets or
  initialises the chip as a side effect.
- A chip without an ID register checks the closest equivalent (a reset value, a known status bit) and documents it.
- Destructive operations (firmware update, OTP write, factory reset) MUST take their data or confirmation
  explicitly. No default argument may trigger them.

## Config and Kconfig

```cpp
struct Config {
  Oversampling pressure_osr = Oversampling::X8;   // datasheet default unless the README says why not
  uint16_t odr_mhz = 50'000;                      // units as suffixes
  uint32_t ready_timeout_ms = 10;
};
```

- Run-time configuration MUST be one `Config` struct with unit-suffixed fields and defaults taken from the
  datasheet. The struct is passed to `Initialize()`; individual setters MAY exist for values that change at run
  time.
- What differs between products (which channels are used, which features are on, a profile table) is a field of
  `Config` (a mask, a `std::span` passed in), never a compile-time switch for one product
  ([layers.md](layers.md#product-specific-code)).
- Kconfig is an optional ESP-IDF layer, in `_config/Kconfig` (registered with `KCONFIG` by the root
  `CMakeLists.txt`). If a driver ships a `Kconfig`, the `CONFIG_<CHIP>_*` values MUST be read in
  exactly one header, `inc/<chip>_kconfig.hpp`, which produces a `Config` (`<chip>::KconfigDefaults()`). Kconfig
  values MUST NOT appear in public signatures, constructors or other headers.
- A driver that reads `CONFIG_*` without shipping the `Kconfig` that defines it is a defect.
- ESP-IDF projects set values through `sdkconfig.defaults`; a full `sdkconfig` is not committed.

## Memory and threads

([ADR-0004](../adr/0004-no-heap.md))

- No heap (`new`, `malloc`, `std::vector`, `std::string`), no exceptions, no RTTI, no `std::function`, no
  `printf`-family calls, no `static` mutable state (including function-local statics and report buffers).
- Callbacks are a function pointer plus a `void*` context: `using DataReadyFn = void (*)(void* ctx);`.
- Buffers are members sized by `constexpr` limits, or caller-provided `std::span`.
- The driver is not thread-safe and MUST NOT lock. One driver object is used from one thread at a time; kb-core
  handlers own the locking. The driver MUST NOT call an RTOS.
- The driver MUST NOT sleep except through the port's delay hooks.

## Large chips

A chip with many subsystems (a motor controller, an IMU with a sensor hub) MAY split its API into sub-object
facades held by the driver (`driver.telemetry().ReadSupplyMv()`). Each facade follows this contract; they share
the driver's port, lifecycle and `Error`.

## Build, export and versioning

- C++20 ([ADR-0010](../adr/0010-cpp20.md)), `target_compile_features(... cxx_std_20)`. MIT
  ([ADR-0009](../adr/0009-licensing.md)).
- `cmake/<chip>_build_settings.cmake` MUST be the single source of the version (`<CHIP>_VERSION_MAJOR`,
  `_MINOR`, `_PATCH`), the target name and the source list. `project()`, the package version, the generated
  `<chip>_version.h`, `PROJECT_NUMBER` in `_config/Doxyfile` and the version in `driver.yml` all come from it or
  are checked against it, and a test checks that every copy agrees.
- The target MUST have `EXPORT_NAME <chip>` and a `<chip>::<chip>` alias, so `<chip>::<chip>` works after both
  `add_subdirectory()` and `find_package(<chip>)`.
- Install rules MUST install every header the umbrella header includes, the `.ipp`, the generated version header
  and the package config.
- Options are `<CHIP>_BUILD_TESTS` (host tests and doc snippets, `OFF` by default) and `<CHIP>_ENABLE_WARNINGS`.
- The root `CMakeLists.txt` MUST also be the ESP-IDF component: under `ESP_PLATFORM` it calls
  `idf_component_register()` from the build settings, with `KCONFIG ${CMAKE_CURRENT_LIST_DIR}/_config/Kconfig`, and
  returns before `project()`. This is build glue, not driver code: `inc/` and `src/` never test `ESP_PLATFORM`.
  ESP-IDF projects use the repository through `EXTRA_COMPONENT_DIRS`, a checkout under `components/`, or a
  component-manager git dependency; there is no wrapper component and no `idf_component.yml` (added only if
  registry publishing is chosen).
- Every repository MUST use the shared CI, `kokeb-labs/ci-tools/.github/workflows/<name>.yml@v1`.
- The version is SemVer 0.x until the API is declared stable ([release.md](release.md)).

## Metadata: `driver.yml`

Every driver carries `driver.yml` at the root. kb-core builds its compatibility file, `catalog/compat.yml`, from
the `driver.yml` of each pinned driver ([release.md](release.md#release-trains)); the file drives the CMake MCU
gate, the `kb` command-line tool and the web configurator.

```yaml
name: zp100
version: 0.2.0             # checked against cmake/zp100_build_settings.cmake
bus: [i2c]                 # spi, i2c, uart, adc, pio (a timed bit stream), or a protocol (canopen)
mcus: [any]                # any, or the families it needs: [esp32]
peripheral: null           # the MCU peripheral it needs, with mcus: RMT
kb_core_min: 0.1.0         # the oldest kb-core whose handler and adapters work with this version
```

- `mcus` is `[any]` unless the driver needs one MCU's peripheral; then it names the families and `peripheral`
  names the peripheral, which becomes a row of the MCU gate table (`"WS2812:ESP32:RMT"`).
- `kb_core_min` is the only mention of kb-core in a driver, and it is metadata: the driver's code never depends
  on kb-core.
- CI checks the file against the build settings and the examples it builds.

## Tests

- `tests/mock_<chip>.hpp`: a register-level model of the chip implementing the port, used by every host test.
- A host suite built on gcc and clang with `-Wall -Wextra -Werror -fno-exceptions -fno-rtti`, run by the shared
  host-test workflow. It covers: every public call before `Initialize()` (`NotInitialized`), the chip-ID
  mismatch, a failing port hook on every call path (`Bus`), argument validation, and the register traffic of each
  feature.
- `tests/docs/`: every code block on the documentation site compiles here (`<!-- generated: ... -->` regions).
- `tests/install_consumer/`: installs the driver and builds a consumer with `find_package(<chip>)` and
  `<chip>::<chip>`.
- A version test: the CMake version, `_config/Doxyfile`, `driver.yml` and `GetDriverVersion()` agree.
- `examples/host/` is built with the test flags and run by the host tests, and CI builds every
  `examples/<platform>/` (the shared ESP32 example-build workflow for ESP32).

## Docs

The driver page set in [docs.md](docs.md), plus:

- Doxygen with `EXTRACT_ALL = NO` and warnings as errors on `inc/`: every public symbol is documented.
- The quickstart checks every return value.
- The Porting page shows a complete port for each bus, compiled in `tests/docs/`.
- The API guide lists the `Error` values each call can return.

## Exceptions

### MCU-bound drivers

A chip that only works with one MCU peripheral (WS2812 LEDs timed by the ESP32 RMT) still gets a platform-free
driver: it builds frames, encodes pixels and checks arguments, and reaches the peripheral through its port. The
MCU-specific part is not in the driver:

- In kb-core, the peripheral backend lives in `interfaces/mcu/<family>/` behind a `Base*` interface, and the
  driver is listed in the MCU gate table ([layers.md](layers.md#mcu-specific-code)).
- In the driver repository, the backend is the port in `examples/<family>/`.
- `driver.yml` names the families and the peripheral; the README and Contract page say the driver is MCU-bound.
- `examples/host/` MAY be replaced by host tests over a mock of the peripheral.

The driver keeps the repository shell, the root layout, the error model, the lifecycle and the naming. It MUST
NOT include the vendor SDK in `inc/` or `src/`.

### Protocol clients

A driver for a device reached over a protocol rather than a chip (a fictional motor-controller node over CANopen)
skips the chip-specific rules: chip-ID check, register model, datasheet defaults and the register mock. It follows
everything else: namespace, port, `Result<T>` and `Error`, lifecycle, no heap, build, `driver.yml`, tests and docs.
Its `Initialize()` checks the remote identity (device type, vendor ID) instead of a chip ID.
