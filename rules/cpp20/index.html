C++20 profile¶

The C++20 language and library features Kokeb Labs code may use, the rules each one comes with, and the ones it may not use, as numbered guidelines. They extend MISRA C++:2023, which is written for C++17, to the C++20 our code is written in, and they define exactly what deviation MD-CPP-001 covers. The C++20 profile page explains each feature's verdict; categories follow MISRA's model (mandatory and required guidelines are must, advisory ones should).

KB-CPP20-001: Strict ISO C++20, with a conformance build on every target compiler¶

Proposed

Category required; warns until 2027-03-01, then fails CI.

MUST · driver, template, library, hal, firmware · since 1.0 · enforced from 2027-03-01

Every target a repository builds itself (library, tests, fuzzers, host examples, install consumer) compiles as ISO C++20 with CMAKE_CXX_EXTENSIONS OFF and -pedantic-errors. Every public header also compiles on its own at -std=c++20 -pedantic-errors with each compiler the repository ships for: host GCC and Clang, Arm GCC in the cross-build, and the ESP-IDF toolchain, whose own default dialect is newer (a header self-check compiled at -std=c++20 inside the ESP-IDF build).

Why: MD-CPP-001 deviates Rule 4.1.1 for C++20, not for whatever a framework enables. CMake's default leaves extensions on (-std=gnu++20), and ESP-IDF builds as gnu++23 or gnu++26, so without a strict build a GNU extension or a C++23 feature compiles on one toolchain and breaks on another.

Verified by:

  • cpp20-profile/cmake-extensions (implemented): a source check of the C++20 profile (rules/cpp20.yml); the parameter names it: forbidden-features (no coroutines, modules, range views, <format>, char8_t, C++23 features, feature-test macros, [[fallthrough]], and in drivers no <=>, <source_location>, variant, any, function or [[no_unique_address]]), cmake-extensions (every CMakeLists.txt that builds a target sets CMAKE_CXX_EXTENSIONS OFF, itself or in a parent directory), nodiscard-error (Error enumerations and Result types are [[nodiscard]]), inline-requires (no requires-expression in an if constexpr condition), kconfig-leaf (no header includes the Kconfig header)
  • forbidden-patterns/cmake-cxx-standard (implemented): a source scan for a construct the handbook bans; the parameter names the pattern set
  • compiler-warnings/-pedantic-errors (implemented): the build is warning-free with the named flag and -Werror
  • strict-dialect (implemented): every public header, and through the driver header its src/*.ipp, compiles as ISO C++20 (-std=c++20 -pedantic-errors, extensions off) with each compiler the repository ships for: host GCC and Clang, Arm GCC in the cross-build, and the ESP-IDF toolchain through a header self-check built at -std=c++20 inside the ESP-IDF build, whose own default dialect is newer

See also: MISRA C++:2023 Rule 4.1.1; MISRA C++:2023 Rule 4.1.2

KB-CPP20-002: Only profile features; nothing from C++23 or later¶

Proposed

Category required; warns until 2027-03-01, then fails CI.

MUST · driver, template, library, hal, firmware · since 1.0 · enforced from 2027-03-01

Target code uses only the language and library features this profile marks *Use* or *Use with rules*, under the guidelines attached to them, and library headers only from the layer's ADR-0017 subset. No feature of C++23 or later is used, even where a framework's dialect accepts it (std::to_underlying, std::byteswap, std::expected, if consteval, [[assume]], deducing this, the uz literal suffix).

Why: MD-CPP-001 must name what it covers, and a feature that enters without review enters the safety case unexamined. Our own detail::ToUnderlying replaces the C++23 helper at no cost.

Verified by:

  • include-allowlist/driver (implemented): a script over the include graph that fails on a header outside the allowed set for the directory; the parameter names the table (driver, hosted, kb-core, handlers, hal-boundary)

KB-CPP20-003: Nothing C++20 deprecates¶

Proposed

Category required; warns until 2027-03-01, then fails CI.

MUST · driver, template, library, hal, firmware · since 1.0 · enforced from 2027-03-01

No construct deprecated by C++20: compound assignment or ++/-- on a volatile object, volatile parameters and return types, implicit capture of this through [=], a comma expression in a subscript, arithmetic or comparison between two different enumeration types or between an enumeration and a floating-point type.

Why: Deprecated features are candidates for removal and are deprecated because they mislead: a volatile read-modify-write is not atomic, and [=] does not copy the object.

Verified by:

  • compiler-warnings/-Wdeprecated (implemented): the build is warning-free with the named flag and -Werror
  • compiler-warnings/-Wdeprecated-enum-enum-conversion (implemented): the build is warning-free with the named flag and -Werror
  • compiler-warnings/-Wdeprecated-enum-float-conversion (implemented): the build is warning-free with the named flag and -Werror
  • clang-tidy/cppcoreguidelines-misleading-capture-default-by-value (implemented): a clang-tidy check from config/.clang-tidy, run with the CMake compile database

See also: MISRA C++:2023 Rule 4.1.2; MISRA C++:2023 Rule 10.1.2

KB-CPP20-004: No feature-test macros to choose behaviour¶

SHOULD · driver, template, library · since 1.0

Shared code does not test __cpp_ or __cpp_lib_ macros or include <version> to pick an implementation. There is one language level; a missing feature is a toolchain problem, not a branch.

Why: Two code paths per feature means one of them is untested on any given CI matrix.

Verified by:

  • cpp20-profile/forbidden-features (implemented): a source check of the C++20 profile (rules/cpp20.yml); the parameter names it: forbidden-features (no coroutines, modules, range views, <format>, char8_t, C++23 features, feature-test macros, [[fallthrough]], and in drivers no <=>, <source_location>, variant, any, function or [[no_unique_address]]), cmake-extensions (every CMakeLists.txt that builds a target sets CMAKE_CXX_EXTENSIONS OFF, itself or in a parent directory), nodiscard-error (Error enumerations and Result types are [[nodiscard]]), inline-requires (no requires-expression in an if constexpr condition), kconfig-leaf (no header includes the Kconfig header)

KB-CPP20-005: Every template parameter is constrained by a named concept¶

Proposed

Category required; warns until 2027-03-01, then fails CI.

MUST · driver, template, library · since 1.0 · enforced from 2027-03-01

Each type template parameter in target code has a constraint: a named concept in the template head (template <SpiPort Port>) or a requires clause. A callable parameter is constrained with std::invocable and its result type.

Why: An unconstrained parameter accepts anything; misuse is reported deep inside the body, or compiles.

Verified by:

  • codeql/unconstrained-template (planned): a query of the Kokeb CodeQL pack for C++ over the CMake build; the parameter names the query (for example shift-range, compound-narrowing, enum-from-integer, unbounded-loop, pointer-length-parameter)
  • review: Every new template parameter names its concept.

See also: MISRA C++:2023 Rule 17.8.1; MISRA C++:2023 Dir 0.3.2

KB-CPP20-006: Port concepts check the exact hook signature and noexcept¶

Proposed

Category required; warns until 2027-03-01, then fails CI.

MUST · driver, template · since 1.0 · enforced from 2027-03-01

A port concept accepts only hooks with exactly the signature on the driver's Porting page: each argument is probed with a type that converts to the documented parameter type and to nothing else, each compound requirement states noexcept, and each result type is checked with std::same_as. Compile-fail tests prove that a narrowed parameter and a missing noexcept are rejected.

Why: A concept that probes with plain values is satisfied by Transfer(..., uint16_t len), so the driver's length is truncated at every call without a diagnostic; KB-CPP-035 asks for noexcept, and the concept is where it can be proved.

Verified by:

  • compile-fail-tests (implemented): a misuse of the public API is a compile error, proved by a test that must fail to compile
  • codeql/port-hook-signature (planned): a query of the Kokeb CodeQL pack for C++ over the CMake build; the parameter names the query (for example shift-range, compound-narrowing, enum-from-integer, unbounded-loop, pointer-length-parameter)
  • review: Each port concept probes with detail::Exactly<T> and states noexcept on every hook.

See also: MISRA C++:2023 Rule 7.0.6; MISRA C++:2023 Rule 0.1.2; MISRA C++:2023 Rule 4.1.3

Explained in: standards/cpp20-profile.md

KB-CPP20-007: Optional hooks use named detection concepts; a misdeclared hook is an error¶

Proposed

Category required; warns until 2027-03-01, then fails CI.

MUST · driver, template · since 1.0 · enforced from 2027-03-01

Each optional hook has a named concept Has<Hook> in <chip>::detail that checks argument types exactly, the result type and noexcept, and a Declares<Hook> concept that only tests the name; the driver static_asserts !Declares<Hook> || Has<Hook>. No anonymous requires-expression appears in an if constexpr condition.

Why: Detection that silently falls back when a hook is misdeclared turns a wiring mistake into a missing delay or a dropped GPIO error; one named concept is also what KB-CPP-036 asks for.

Verified by:

  • cpp20-profile/inline-requires (implemented): a source check of the C++20 profile (rules/cpp20.yml); the parameter names it: forbidden-features (no coroutines, modules, range views, <format>, char8_t, C++23 features, feature-test macros, [[fallthrough]], and in drivers no <=>, <source_location>, variant, any, function or [[no_unique_address]]), cmake-extensions (every CMakeLists.txt that builds a target sets CMAKE_CXX_EXTENSIONS OFF, itself or in a parent directory), nodiscard-error (Error enumerations and Result types are [[nodiscard]]), inline-requires (no requires-expression in an if constexpr condition), kconfig-leaf (no header includes the Kconfig header)
  • compile-fail-tests (implemented): a misuse of the public API is a compile error, proved by a test that must fail to compile

See also: MISRA C++:2023 Rule 0.1.2; MISRA C++:2023 Rule 9.6.5

KB-CPP20-008: One dependent-false helper¶

SHOULD · driver, template, library · since 1.0

A branch that must never be instantiated fails with static_assert(detail::kAlwaysFalse<T>, "..."), from one template <typename> inline constexpr bool kAlwaysFalse = false; per repository, not with ad hoc spellings such as sizeof(T) == 0.

Why: C++20 does not allow static_assert(false) in a discarded template branch; one named helper states the intent.

Verified by:

  • review: Discarded branches use detail::kAlwaysFalse.

See also: MISRA C++:2023 Rule 0.0.1

Explained in: standards/cpp20-profile.md

KB-CPP20-009: Code that does not depend on the port lives outside the class template¶

SHOULD · driver, template, library · since 1.0

Register encoders and decoders, validation, CRC, unit conversion and error text are namespace-scope constexpr functions, not members of the driver's class template.

Why: A member of Driver<Port> is emitted once per port type; a free constexpr function is emitted once or folded away, and can be proved with static_assert.

Verified by:

  • codeql/port-independent-member (planned): a query of the Kokeb CodeQL pack for C++ over the CMake build; the parameter names the query (for example shift-range, compound-narrowing, enum-from-integer, unbounded-loop, pointer-length-parameter)
  • review: A static member that never names the port moves out.

See also: MISRA C++:2023 Rule 6.2.3

Explained in: standards/cpp20-profile.md

KB-CPP20-010: Abbreviated function templates are constrained and stay out of the public API¶
